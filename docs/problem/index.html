01 · 为什么难

六类约束不是排队出现，而是同时咬合。

波束选择会改变可用速率，资源成员关系会影响共享，缓存上限又会改变每一步的真实收益。任何局部修改，都可能让原本合法的分配越界。

系统模型

一次调度，同时决定波束掩码与每个资源上的用户集合。

论文用 U、R、T、P 表示用户、资源、子带与波束。每个用户具有有限缓存 Bᵤ、基础链路质量 γᵤ 和波束能力 cᵤ,ₚ；每个资源显式属于一至两个子带，两个成员可以不相邻。

U用户 R资源 T子带 P波束

调度器每个周期回答什么？

激活哪些子带—波束组合，并把哪些用户放到每个资源上；结果必须在截止时间前完整序列化且通过全部约束。

目标：最大化受缓存上限约束的传输量

收益由实际可交付流量决定，而不是无限累加链路分数。

F(α,G) = Σu∈U min { Bu, Σr:u∈Gᵣ q(zu,r) }

α 表示子带—波束激活，Gᵣ 表示资源 r 上的合法用户集合。只有在外部截止时间 D 前通过全部约束并完成序列化，输出才获得正效用。

有效链路值先经过阶梯函数，再计入传输量。

这个 q(z) 是单快照的确定性流量抽象，不是连续物理层速率定律。

约束结构

把六类约束归入三个会相互反馈的层次。

无线激活决定可用能力，资源共享决定组合合法性，交付契约再把有限缓存与硬截止时间施加到完整输出上。

无线激活

  • 全局波束预算
  • 子带波束掩码

链路与共享

  • 阶梯式链路自适应
  • 兼容组共享约束

交付契约

  • 有限用户缓存
  • 硬截止时间

设计动机

传统“先改再修”的风险

如果细化直接写入当前解，超时或验证失败时可能只留下一个半成品。FPTR 把候选解隔离开，让失败只损失这次尝试，不损坏已经可用的结果。

直接修改 live solution

局部编辑 → 尚未修复全部约束 → 计时结束 → 当前解不可发布。

隔离候选 + 事务门

incumbent 保持不变 → 私有候选完成并验证 → 通过则整体提交，否则整体丢弃。
